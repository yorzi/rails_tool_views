# ADR 008 — Explicit Surface lifecycle and conservative retention

Date: 2026-10-19. Status: accepted implementation design for owner-authorized 0.3. FR-04/05/06/07/08, NFR-02/05. No notification catalog or product-intent change; external Specs remain pinned.

A host explicitly closes a finished Surface or abandons pending/failed work. Domain completion is not inferred from UI state. Reads and correlated presentations remain authorized and readable; new actions stop, exact already-committed receipts replay under the existing policies. Closing advances revision once. First termination/deadline wins; no reopening, no automatic expiry. nil deadline means indefinite retention. Host policies receive :close or :abandon in addition to the normal read check. No Engine HTTP endpoint or agent tool grants these operations.

Actions, delivery claims and lifecycle changes lock Surface first, then interaction. Callbacks remain outside transactions. A delivering status blocks termination even after lease expiry. Lease takeover does not prove that an old callback stopped: persist delivery_uncertain on every takeover, and conservatively backfill old delivering/multiple-attempt rows. Terminal acknowledgments never clear it. Automatic lifecycle refuses these rows, including after terminal status. Recovery/attested resolution is deferred; no force flag or guessed timeout grants deletion. This guard protects retention without claiming exactly-once remote effects or repairing the older delivery acknowledgment protocol.

Opt-in cleanup requires explicit owner scope, cutoff, host retention policy, elapsed deadline and bounded batches. Preview defaults to no writes. Under the Surface lock, remove Engine payloads/receipts/interactions atomically, but retain the Surface ID/owner/component lifecycle tombstone and Presentation correlation/digest guards. A purged Surface returns 410, a different owner 404; old correlation cannot allocate another Surface. This is payload cleanup, not full record erasure or disk compaction. Domain records are never deleted. Full backup and remaining opaque identifier retention stay host-owned.

The additive migration leaves old views active, preserves snapshots/receipts and quarantines ambiguous old delivery histories. Stop all old workers before migration/restart; old runtimes do not enforce closure. Migration down refuses once any view was closed, because dropping guards could reopen work and purged data cannot be reconstructed. New installs copy both migrations; existing hosts use Rails' standard railties:install:migrations task.

Alternatives: delete whole graphs (correlation can recreate business work), prune receipts independently (retries lose their durable guard), infer terminal state from last action/status/age (no host retry contract), or hold provider calls inside transactions (long locks and still no network atomicity). Retained metadata costs rows but gives an explicit safe boundary. Revisit after 0.4 recovery evidence, never by silently clearing uncertainty or shortening deadlines.
